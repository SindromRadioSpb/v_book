## Primary objectives

### A. Infrastructure research
Research the real infrastructure and execution flow for:
- niqqud generation
- translation
- TTS / audio generation
- all tabs/views where these capabilities are available
- worker execution model
- database access patterns
- pagination / filters / sorting / refresh logic
- caching opportunities and risks
- handling of large projects / large databases

### B. Functional test coverage
Run end-to-end tests of niqqud, translation, and TTS across all relevant tabs/views in the application.

The analysis must answer:
- Which tabs/views expose each capability?
- Are they using the same or different execution paths?
- Are all flows worker-safe and non-blocking?
- Are there duplicate implementations or inconsistent pipelines?
- Are some tabs significantly slower than others?
- Are there avoidable repeated DB reads, counts, refreshes, or provider initializations?

### C. Timing and bottleneck profiling
Measure and document timings for:
- application startup on the target DB
- project opening / project switching
- tab opening
- initial load of heavy views
- pagination changes
- filtering / search
- niqqud request execution
- translation request execution
- TTS request execution
- repeated execution with warm state
- repeated execution with cache hits where applicable
- refreshes after batch operations
- counts on large tables
- any expensive overlay / reconciliation logic

You must identify:
- cold-path costs
- warm-path costs
- repeated costs that should be cached
- UI-thread work that must move off-thread
- DB queries that are acceptable vs pathological
- operations that degrade non-linearly with project size

### D. Cache strategy analysis
Determine what is actually reasonable to cache when the application is connected to a **large DB with very large projects**.

Analyze candidates such as:
- provider/resource initialization state
- model availability/resource checks
- expensive metadata summaries
- project statistics
- total counts
- filtered counts
- last-used view state
- normalized text / lookup keys
- translation results
- niqqud results
- TTS metadata / audio asset metadata
- reusable query results
- frequently accessed small dictionaries / mapping tables
- UI-visible DTO snapshots for current page only
- precomputed aggregates
- background-populated summary tables

For every cache candidate, specify:
- what can be cached
- cache key design
- invalidation triggers
- stale-data risks
- expected win
- memory footprint risk
- whether cache belongs in RAM, SQLite table, persisted app cache, or precomputed materialized structure

### E. Large-scale readiness
Answer the hard question:

**What must be done if a project contains millions of rows and simple optimizations are not enough?**

Propose requirements and strategies needed so the application remains responsive without freezes or hangs.

Include:
- strict UI-thread safety requirements
- bounded page loading
- async count strategies
- delayed / background totals
- summary tables / pre-aggregates
- selective hydration
- lazy detail loading
- projection-only queries
- covering indexes
- denormalized helper tables where justified
- write-path implications
- memory ceilings
- cache ceilings
- cancellation / pause / resumability
- progress visibility
- batch size constraints
- large-project UX adaptations

### F. Radical options
If simple optimizations, conventional caching, indexing, and workerization are still insufficient, propose more radical architectural options.

Examples of the kind of options to consider:
- materialized summary tables
- background indexing pipelines
- offline precomputation stages
- project sharding / logical partitioning
- archive / cold-storage mode for stale data
- split “active project” vs “historical corpus” storage
- separate analytics DB or read-optimized mirror
- per-project derived caches
- service-process separation for heavy NLP/TTS/translation work
- queue-based job orchestration
- out-of-process workers
- incremental view models
- snapshotting
- project-open warmup pipelines
- optional “large project mode”
- reduced live totals / deferred expensive metrics
- hard UX limits for pathological cases

For each radical option, describe:
- what problem it solves
- migration cost
- implementation complexity
- regression risk
- operational cost
- user experience trade-offs
- whether it should be optional or mandatory
