# Epic 5B — Layered Extraction Modes: User Guide & Design Reference

**Дата завершения:** 2026-03-22
**Схема:** v46 (migration 046 — `ngram_n_set` на `term_cluster`)
**Commits:** 9212e57 → b726ec1 (5 коммитов, PATCH-06..10)

---

## Зачем это нужно

До Epic 5B переизвлечение терминов всегда было операцией Full Overwrite:
все кластеры проекта удалялись, затем создавались заново.
Это приводило к двум проблемам:

1. **Нельзя было изолированно переизвлечь один n-слой** (например, только биграммы).
   Пользователь вынужден пересобирать всё — даже если изменился только один параметр.

2. **Нельзя было добавить новые паттерны без потери существующей курации.**
   После смены параметров вся кюрированная работа (pinned_translation, curation_status)
   оставалась на месте (Epic 5A защитила TM-записи), но кластеры пересоздавались заново,
   сбрасывая статусы `approved`/`rejected`.

Epic 5B вводит три явных режима, которые пользователь выбирает перед запуском.

---

## Три режима извлечения

### 1. Full Overwrite — полная пересборка

**Когда использовать:**
- Первое извлечение для нового проекта.
- Корпус был существенно пополнен или изменён.
- Нужно начать курацию с нуля.
- Изменились параметры, влияющие на всю структуру кластеров (min_freq, NP).

**Что происходит:**
1. Показывается impact preview (если есть TM-записи с активными ссылками на кластеры).
2. Пользователь подтверждает.
3. Все кластеры и ngrams проекта удаляются.
4. Запускается полное переизвлечение — chunked staged pipeline.
5. Создаются новые кластеры.

**Что сохраняется:**
- TM-записи (`tm_entry`) — всегда, они живут независимо.
- `promoted_from_cluster_id`, `promoted_at_params_hash` — навсегда (провенанс).
- После завершения: TM-записи, у которых `cluster_id` указывал на удалённые кластеры,
  переходят в статус `source_cluster_missing` (отображается в TM панели как красный ●).

**Что сбрасывается:**
- Все `term_cluster` — удаляются и пересоздаются.
- Кюрационные поля на кластерах (`curation_status`, `pinned_translation`, etc.) теряются,
  потому что кластер — новый объект с новым `cluster_id`.

> **Совет:** Завершайте и экспортируйте курацию перед Full Overwrite.
> TM-панель сохраняет переводы в `tm_entry` — они не теряются. Теряется только
> кюрационный статус на самих кластерах (Terms view).

---

### 2. Merge — добавление без удаления

**Когда использовать:**
- Хотите добавить новые n-size (например, триграммы к уже извлечённым биграммам).
- Обработали дополнительные документы и хотите включить новые термины.
- Хотите сохранить всю кюрацию и добавить новые паттерны поверх.

**Что происходит:**
1. `_clear_existing_terms` **не вызывается** — существующие кластеры и ngrams не трогаются.
2. Запускается extraction для указанных параметров.
3. Новые ngrams: вставляются через INSERT OR IGNORE — если ngram с такими
   `(project_id, n, surface_text, source_kind)` уже существует, он пропускается.
4. Новые кластеры: если кластер с таким `canonical_key` уже есть — сохраняется,
   в него добавляются только новые ngram-члены.
   Если кластер новый — вставляется полностью.
5. `clusters_created` в отчёте: только реально новые кластеры (не затронутые существующие).

**Что сохраняется:**
- Все существующие кластеры — полностью (включая curation_status, pinned_translation).
- Частоты существующих кластеров — **не обновляются** (additive-only семантика).
- TM-записи — не затрагиваются.

**Ограничения:**
- Частоты существующих ngrams и кластеров не пересчитываются.
  Merge — это "добавить новое", не "обновить старое".
- Если в корпусе изменились частоты, используйте Full Overwrite.

> **Типовой сценарий:** сначала извлекли биграммы, покюрировали,
> теперь хотите добавить триграммы. Выбираете Merge с `ngram_ns=(3,)` —
> биграммные кластеры остаются нетронутыми.

---

### 3. Replace Layer — замена конкретного n-слоя

**Когда использовать:**
- Нужно переизвлечь **только** биграммы (или только триграммы), не трогая другие слои.
- Изменили параметры, специфичные для конкретного n-size.
- Хотите "освежить" один слой без полной пересборки.

**Что происходит:**
1. Вычисляется `target_n_set = canonical_ngram_n_set(ngram_ns)` —
   например, `"[2]"` для биграмм или `"[2,3]"` для bigrams+trigrams.
2. Удаляются `term_cluster WHERE ngram_n_set = target_n_set` (CASCADE удаляет members).
3. Удаляются `ngram WHERE source_kind='ngram' AND n IN ngram_ns`.
4. Запускается chunked extraction **только** для указанных `ngram_ns`.
5. NP-кластеры (`ngram_n_set IS NULL`) не трогаются.
6. Кластеры других n-слоёв (например, `"[3]"` при Replace `"[2]"`) не трогаются.
7. `resume_latest=False` — предыдущие checkpoint'ы для этого проекта не используются
   (они стали невалидными после удаления слоя).

**Что сохраняется:**
- NP кластеры — не затрагиваются.
- Кластеры других n-размеров — не затрагиваются.
- Кюрация на сохранившихся кластерах — не затрагивается.
- TM-записи — не затрагиваются.

**Что сбрасывается:**
- Кластеры с `ngram_n_set` точно равным `target_n_set`.
  Важно: кластер `"[2,3]"` (bigrams+trigrams) **не** удаляется при Replace Layer `"[2]"`.
  Replace Layer работает только по точному совпадению n-set.
- Ngrams для указанных n-sizes (source_kind='ngram').

**Ограничения:**
- NP-слой игнорируется: `include_np` принудительно `False`.
  Для замены NP-слоя используйте Full Overwrite.
- Частоты TM-записей могут разойтись с пересозданными кластерами.
  Это ожидаемо — TM-записи имеют независимый lifecycle.

> **Типовой сценарий:** поняли, что min_freq для триграмм был слишком низким,
> шумных кластеров много. Выбираете Replace Layer с `ngram_ns=(3,)` и более высоким
> min_freq. Биграммные кластеры и их курация остаются нетронутыми.

## Таблица сравнения

| | Full Overwrite | Merge | Replace Layer |
|---|---|---|---|
| Удаляет все кластеры | ✅ | ❌ | Только целевой n-set |
| Удаляет ngrams | ✅ | ❌ | Только для указанных n |
| NP кластеры | Удаляются | Сохраняются | Сохраняются |
| Кюрация кластеров | Теряется | Сохраняется | Сохраняется (у оставшихся) |
| TM-записи | Сохраняются | Сохраняются | Сохраняются |
| Impact preview | ✅ (если есть linked TM) | ❌ | ❌ |
| Checkpoint resume | ✅ | ✅ | ❌ (forced) |
| Пересчитывает частоты | ✅ | ❌ | ✅ (для целевого слоя) |

## Что хранит ngram_n_set

Каждый `term_cluster` теперь имеет поле `ngram_n_set` — canonical JSON-массив n-размеров,
из которых составлен кластер.

| ngram_n_set | Значение |
|-------------|---------|
| `"[2]"` | Кластер из bigrams (2-граммы) |
| `"[3]"` | Кластер из trigrams (3-граммы) |
| `"[2,3]"` | Кластер из bigrams + trigrams вместе |
| `NULL` | Кластер из NP-чанков (без n-граммного слоя) |

Формат: отсортированный по возрастанию, без пробелов, компактный JSON.
Расширяемо на 4-граммы (`"[4]"`) без изменения схемы.

Replace Layer удаляет только кластеры с **точным** совпадением `ngram_n_set`.
Это значит, что кластер `"[2,3]"` не пострадает при Replace Layer `"[2]"`.

## Типовые сценарии

### Сценарий A: Постепенное наращивание слоёв

```
Шаг 1: Extract → Full Overwrite, ngram_ns=(2,), include_np=False
        → получаем биграммные кластеры, курируем

Шаг 2: Extract → Merge, ngram_ns=(3,), include_np=False
        → добавляем триграммы поверх, биграммная курация не затронута

Шаг 3: Extract → Merge, include_np=True, ngram_ns=()
        → добавляем NP-чанки, всё остальное сохраняется
```

### Сценарий B: Переизвлечение только триграмм

```
Текущее состояние: кластеры "[2]" (биграммы) + "[3]" (триграммы), часть скюрирована

Действие: Extract → Replace Layer, ngram_ns=(3,)

Результат:
  - "[3]" кластеры и их ngrams удалены
  - "[3]" заново извлечены с новыми параметрами
  - "[2]" кластеры — не тронуты
  - NP кластеры — не тронуты
  - TM-записи, ссылавшиеся на удалённые "[3]" кластеры → source_cluster_missing
```

### Сценарий C: Полная пересборка после пополнения корпуса

```
Текущее состояние: большой проект, значительная курация в TM

Действие: Extract → Full Overwrite (confirm impact preview)

Результат:
  - Все кластеры удалены и пересозданы
  - TM-записи сохранены; linked-статусы обновятся по новым cluster_id
    (через promote снова, если нужно)
  - promoted_from_cluster_id сохранён — audit trail не потерян
```

## Состояния TM-записей после операций

После любого режима извлечения TM-записи могут оказаться в одном из трёх состояний
(отображается в TM панели, колонка "Src"):

| Статус | Индикатор | Условие |
|--------|-----------|---------|
| `linked` | ● зелёный | `cluster_id IS NOT NULL` — кластер жив |
| `source_cluster_missing` | ● красный | `cluster_id IS NULL AND promoted_from_cluster_id IS NOT NULL` |
| `manual` | ● серый | `cluster_id IS NULL AND promoted_from_cluster_id IS NULL` |

`source_cluster_missing` — нормальное состояние после Full Overwrite или Replace Layer.
Запись жива, перевод сохранён. При следующей promote через UI ссылка восстановится.

## UX-контракт: что видит пользователь

### Выбор режима

В Terms view, перед запуском извлечения — combo box "Extraction Mode":
- **Full Overwrite** (по умолчанию)
- **Merge**
- **Replace Layer**

Выбор сохраняется в QSettings (`terms_view/extraction_mode`) между сессиями.

### Impact preview (только Full Overwrite)

Если выбран Full Overwrite и в проекте есть TM-записи с активными ссылками на кластеры,
показывается диалог подтверждения:

```
Полное переизвлечение удалит X кластеров.
Y TM-записей потеряют активную ссылку (станут source_cluster_missing).
Продолжить?
```

При `Y = 0` — диалог не показывается, старт немедленный.
При Merge и Replace Layer — диалог не показывается (неразрушительные режимы).

## Технические детали (для разработчика)

### Dispatch в `extract_terms_for_project`

```python
extraction_mode = "overwrite"  # default
# "merge"        → chunked path, overwrite=False
# "replace_layer" → _clear_terms_for_layer(ngram_ns) + chunked, resume_latest=False
# backward-compat: overwrite=False с дефолтным extraction_mode → merge
```

### `_clear_terms_for_layer(session, project_id, ngram_ns)`

```sql
-- Удалить кластеры целевого слоя:
DELETE FROM term_cluster
WHERE project_id = ? AND ngram_n_set = '[2]'   -- точное совпадение

-- Удалить ngrams целевых n-размеров:
DELETE FROM ngram
WHERE project_id = ? AND source_kind = 'ngram' AND n IN (2)
-- CASCADE удаляет ngram_project_stat, ngram_component
```

### INSERT OR IGNORE в Merge mode

`_store_staged_ngrams(overwrite=False)`:
- `sqlite_insert(Ngram).on_conflict_do_nothing()` + SELECT для получения ngram_id
- `NgramProjectStat`: вставляется только если ngram был новым

`_insert_cluster_from_members(overwrite=False)`:
- Pre-check `SELECT cluster_id WHERE canonical_key = ?`
- Если существует: link только новые ngram-члены, return 0
- Если нет: обычный INSERT, return 1

### Индекс для Replace Layer

Migration 046 добавляет:
```sql
CREATE INDEX idx_term_cluster_ngram_n_set
ON term_cluster(project_id, ngram_n_set);
```
Оптимизирует скоупированный DELETE при Replace Layer.

## Troubleshooting

**Q: Replace Layer не трогает часть кластеров, хотя они биграммные.**
A: Проверьте `ngram_n_set`. Кластер `"[2,3]"` (из bigrams+trigrams) не удалится
при Replace Layer `"[2]"`. Такие кластеры создаются, когда один canonical_key
встречается и как bigram, и как trigram. Для их замены нужен Replace Layer `"[2,3]"`.

**Q: После Merge частоты не обновились.**
A: Merge — additive-only. Частоты существующих ngrams и кластеров не пересчитываются.
Это по дизайну: Merge сохраняет стабильность кюрации. Для обновления частот — Full Overwrite.

**Q: После Replace Layer в TM появились красные ● записи.**
A: TM-записи, которые ссылались (`cluster_id`) на удалённые кластеры целевого слоя,
перешли в `source_cluster_missing`. Это ожидаемо. После следующей promote через
TM панель (`Source → cluster`) ссылка восстановится на новый кластер.

**Q: Хочу переизвлечь NP-чанки, не трогая ngram-кластеры.**
A: Replace Layer не поддерживает NP-слой (`include_np` принудительно False).
Вариант: Merge с `enable_ngrams=False, include_np=True` — добавит NP без удаления существующих.
Для полной замены NP используйте Full Overwrite.

**Q: Merge завис или выдал ошибку уникальности.**
A: Не должно происходить — Merge использует INSERT OR IGNORE.
Если всё же произошло, проверьте `ngram` таблицу на ручные записи с нарушенными ключами.

## Связь с Epic 5A (TM Safety & Provenance)

Epic 5A и 5B работают в паре:

- **Epic 5A** защищает TM-записи: они переживают любое переизвлечение,
  хранят audit trail (`promoted_from_cluster_id`, `promoted_at_params_hash`),
  и отображают `source_status` в TM панели.

- **Epic 5B** даёт инструмент управления: пользователь выбирает, что именно переизвлекать,
  с явным control над тем, что сохраняется, а что заменяется.

Вместе они превращают переизвлечение терминов из потенциально разрушительной операции
в безопасную и предсказуемую рабочую процедуру.
