# Epic 5D: Terms UX Hardening — Руководство пользователя

> **Версия:** Epic 5D (2026-03-22)
> **Область:** Terms view — весь блок управления порогом и извлечением

---

## Что изменилось и почему это важно

После Epic 5C (кандидаты хранятся все, `min_freq` — фильтр отображения) возникал
ряд практических вопросов:

- Сколько кластеров сейчас скрыто моим порогом?
- Какое распределение частот в моём корпусе?
- Какой порог я использовал прошлый раз?
- Можно ли не хранить единственные упоминания (hapax), если корпус огромный?

Epic 5D отвечает на все четыре вопроса инструментами прямо в интерфейсе.

---

## Новые элементы интерфейса

### Строка статуса с подсчётом скрытых кластеров

```
Clusters: 183 of 524  (Hidden by min freq: 341)
```

При `min_freq > 1` строка статуса дополнительно показывает, сколько кластеров
скрыто текущим фильтром. Это позволяет оценить «стоимость» выбранного порога
без изменения настройки.

При `min_freq = 1` суффикс не показывается — все кластеры видны.

### Строка распределения частот

```
Freq dist:  1→341   2–4→183   5–9→91   10+→34
```

Серая строка под статусом появляется после первого извлечения. Показывает
количество кластеров в каждой полосе частот. Обновляется при каждом поиске.

**Как использовать:**

```
Вижу: 1→341  2–4→183  5–9→91  10+→34

→ min_freq=1:  все 649 кластеров — много для кюрации
→ min_freq=2:  308 кластеров (убираем 341 hapax)
→ min_freq=5:  125 кластеров — рабочий список
→ min_freq=10: 34 кластера — только высокочастотные термины
```

Делаете выбор осознанно, не перебирая значения вслепую.

### Быстрые пресеты

```
[All (1)]  [Common (3)]  [Strict (5)]  [High (10)]
```

Четыре кнопки под спинбоксом. Мгновенно устанавливают `min_freq` и обновляют
таблицу — без переизвлечения, так как данные уже в базе.

### История порогов (Recent)

```
Recent: [▾]  ← показывает: 5 / 3 / 1 / 10 / 2
```

Комбо «Recent:» справа от пресетов помнит до 5 последних значений, которые
вы реально применяли в этом проекте. История отдельная для каждого проекта
и сохраняется между сессиями.

При выборе значения из комбо таблица обновляется мгновенно.

### Чекбокс «Store hapax»

```
[✓] Store hapax
```

По умолчанию включён. Управляет тем, сохраняются ли hapax legomena
(кандидаты с freq=1) при извлечении.

**Когда оставить включённым (дефолт):**
- Корпус небольшой или средний (< 500 документов)
- Вы хотите исследовать редкие термины
- Неважно, сколько места займёт база

**Когда отключить:**
- Корпус большой (> 1000 документов)
- Hapax legomena — шум, не представляющий лингвистического интереса
- Нужно экономить место в базе

**Важно:** смена галочки требует нового Full Overwrite. Два run'а с разными
настройками «Store hapax» не могут resume-иться друг от друга — это
намеренное поведение (содержимое базы было бы семантически несовместимо).

## Всплывающая подсказка Min freq

Наведите курсор на спинбокс Min freq — появится подсказка:

> Display-time filter only. All candidates are stored regardless of this value.
> Change it freely — no re-extraction needed.

Это напоминание о том, что изменение спинбокса — мгновенная и обратимая операция.

---

## Уведомление при resume с изменённым порогом

Если вы изменили `min_freq` между сессиями, а прошлый run не завершился —
в логе появится заметка:

```
Resuming run 42 at doc 180/420 (min_freq changed: 2→5, resume still valid)
```

Resume **всё равно произойдёт**: порог не является частью структурных
параметров run'а и не влияет на сохранённый прогресс.

---

## Предупреждение при большом корпусе + min_freq=1

При попытке запустить Full Overwrite с `min_freq=1` на корпусе больше
200 документов приложение покажет предупреждение:

> Large corpus detected: 420 docs. With min_freq=1 and Store hapax=On,
> all candidates including hapax legomena will be stored. This may create
> significantly more clusters than at min_freq=2+. Continue?

Можно отменить, изменить `min_freq` или отключить «Store hapax» — и только
потом запустить извлечение.

## Типичные сценарии

### Сценарий A: Исследование нового корпуса

```
1. Extract → Full Overwrite → ждёте завершения
2. Смотрите строку Freq dist:  1→N  2–4→N  5–9→N  10+→N
3. Нажимаете [Common (3)] — список сразу перестраивается
4. Нажимаете [Strict (5)] — опять мгновенно
5. Выбираете рабочий порог, начинаете кюрацию
   (hapax legomena по-прежнему в базе — можно вернуться к [All (1)])
```

### Сценарий B: Возврат к проекту после перерыва

```
1. Открываете проект — строка статуса сразу показывает Clusters: X
2. Комбо Recent: показывает [5, 3, 1] — ваши прошлые настройки
3. Выбираете нужное из комбо — таблица обновляется мгновенно
4. Не нужно вспоминать, с каким порогом вы работали
```

### Сценарий C: Большой корпус, нет смысла хранить hapax

```
1. Снимаете галочку "Store hapax"
2. Extract → Full Overwrite
3. В базе сохраняются только кандидаты с freq ≥ 2
4. Min freq = 1 теперь показывает кластеры от 2 (hapax отсутствуют в базе)
5. База меньше, список чище с первого взгляда
```

### Сценарий D: Проверка, сколько кластеров скрыто

```
1. Работаете с min_freq=5, Clusters: 91
2. Строка статуса: Clusters: 91  (Hidden by min freq: 558)
3. Понимаете: при снижении до 1 список вырастет в 7 раз
4. Решаете оставить min_freq=5 — текущий список управляем
```

## Известные ограничения

**Store hapax — только для новых run'ов.** Если проект уже извлечён с
`store_hapax=True`, смена галочки не удалит существующие hapax из базы.
Нужен новый Full Overwrite.

**Freq dist не показывается до первого извлечения.** Если проект пустой —
строка распределения отсутствует.

**Recent history не синхронизируется между устройствами.** История хранится
в локальных QSettings и не является частью базы данных проекта.

## Техническая справка

### Где живут фильтры

```
Storage:  _iter_term_extract_accumulator_batches →
            store_hapax=False → WHERE freq_abs >= 2
            store_hapax=True  → нет фильтра (все кандидаты)

Display:  list_term_clusters → WHERE freq_abs >= min_freq
```

### params_hash после Epic 5D P2.2

Хеш теперь включает `store_hapax`. Два запуска со всеми одинаковыми
структурными параметрами, но разным `store_hapax`, считаются
**разными run'ами** и не могут resume-иться друг от друга.

### algo_version

`_TERM_EXTRACT_ALGO_VERSION = 2` (не изменился в Epic 5D). Все run'ы
v2, созданные до P2.2, имеют `store_hapax=True` в hash payload по дефолту
и корректно resume-ятся новым кодом.
